# Paper Shapers SEO audit — 23 October 2026

## Assessment

The public sites are reachable and have working discovery foundations. The main issues are inconsistent canonical coverage and links, an intermittently incomplete sitemap, and curriculum text quality. Fix these before scaling search landing pages. The previous provisional 60/100 score is not reproducible and is not retained.

This is an audit, not an implementation or deployment. Existing local paper-generation changes are outside this report.

## Scope and method

- Checked the production root, Study and Nearby hosts over unauthenticated HTTPS: landing pages, robots files, sitemaps, URL aliases, authentication responses and deliberately nonexistent paths.
- Initial HTTP matrix: 32 requests. Followed with a bounded 37-URL sample from the initial 19-entry sitemap and landing-page links, then six targeted follow-up requests. Samples overlap; these are not counts of unique content pages. All 37 sampled URLs returned 200, including some protected workflow shells; no broken destination was found in that sample. This was not an exhaustive link or asset crawl.
- Parsed server HTML for titles, descriptions, H1s, canonicals, robots metadata, JSON-LD, links and image attributes. Compared with repository metadata, routing and sitemap code; also rendered representative local pages.
- The web-fetch service initially returned a root-domain 503 and could not open other endpoints. Direct HTTP requests subsequently reached all three hosts. This does not establish an outage or a clean uptime history.
- No Search Console, analytics, backlink database, CrUX field report or authenticated Google inspection was available. No rank, traffic, indexation count or Core Web Vitals score is asserted. SearchFit was not found among available local skills or in plugin discovery; this report uses direct checks and official Google documentation.
- Audit completed around 09:47 UTC. Request timings are one-location observations, not performance benchmarks.

## Prioritized findings

### 1. P1 — Finish canonical coverage and make links consistent

**Confirmed live.** The three Study landing aliases return 200, including `https://papershapers.in/papershapers` and `https://marketplace.papershapers.in/papershapers`, but correctly declare `https://study.papershapers.in/papershapers` as canonical. Nearby aliases similarly declare the marketplace canonical. Subdomain roots rewrite to their portal landing content. These landing pages already have canonical protection; they are not wholly unconfigured.

Coverage falls off on information pages. Both `https://papershapers.in/papershapers/how-it-works` and `https://study.papershapers.in/papershapers/how-it-works` return 200 with **no canonical tag**. Study guide, teacher, contact, membership, mobile, journal index and three sampled journal articles also lack canonicals. Shared privacy, terms and cookies pages are served on multiple hosts without canonicals. `https://www.papershapers.in/` returns 200 with the non-www canonical instead of redirecting.

The umbrella header/footer use configured subdomain links, while product cards, plan links and several footer links use root-relative Study/Nearby paths. Portal navigation also links `/syllabus` on whichever host the visitor is using, although catalogue canonicals consistently point to the root domain.

**Action:** retain the documented portal structure. Define a preferred URL for every public route, add self-referencing canonicals on preferred pages and matching canonicals on supported aliases, and use those URLs in shared links and sitemaps. Add permanent redirects for aliases that can be retired safely, preserving paths and query strings. Do not apply blanket cross-host redirects to authentication, APIs or private workflows; review their origin/session behavior first.

**Acceptance:** all sampled public information pages have one appropriate canonical; public cross-portal links resolve directly to their preferred host; retired aliases permanently redirect without loops. Source: `app/page.tsx`, `app/components/SiteChrome.tsx`, `lib/portals.ts`, `lib/marketplace-seo.ts`, `proxy.ts`, portal page metadata.

[Google canonicalization guidance](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls) recommends consistent internal links and explains canonical/redirect signals. Missing canonicals do not automatically mean a penalty or that Google has indexed every alias.

### 2. P1 — Make sitemap completeness resilient to curriculum availability

**Confirmed live.** Each host's first sitemap response contained 19 entries: five root, nine Study and five Nearby URLs, with no class or subject entries. A later root sitemap response contained **122 entries**, including the curriculum routes. Root `/syllabus` initially timed out at 25 seconds, then loaded successfully; Class 10 and Class 10 Science pages also returned 200.

**Source-supported explanation:** `app/sitemap.ts` asks `getSyllabusCatalog(5000)` and silently falls back to static paths on failure. This can produce a successful but materially smaller sitemap during a curriculum timeout. The exact production timeout cause was not confirmed from server logs. Missing from a sitemap does not by itself prevent indexing because catalogue links still exist.

**Action:** retain a last-known-good public curriculum URL set or equivalent stable discovery source; log failures so operators can distinguish an intentionally empty catalogue from an unavailable service. Keep sitemap generation bounded without silently losing previously known public routes. Recheck actual catalogue coverage before adding new pages.

All three robots files advertise `https://papershapers.in/sitemap.xml`. A cross-host sitemap can work through verified ownership and Search Console submission; that verification is unconfirmed. If relying on robots-based cross-submission, Google's documented route uses separate per-site sitemap files. Either verify and submit the consolidated sitemap for all covered sites, or serve host-specific files and references. Do not label the current sitemap invalid solely because it contains multiple hosts.

**Acceptance:** cold and warm responses retain the intended URL set, private/example content remains excluded, and Search Console reports successful sitemap processing for the covered properties. See [Google sitemap submission guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).

### 3. P1 — Clean curriculum labels before expanding SEO content

**Confirmed live:** `https://papershapers.in/syllabus/class-10/science` has useful class/subject metadata and a correct canonical, but chapter entries include extraction artifacts such as `Chapter 13: Science — Activity 13.1`, `Chapter 8: Science — Figure 8.1`, and `Chapter 4: Science — Carbon and its`. Entries appear in the sequence 10, 11, 12, 13, 1, 2, rather than numeric chapter order.

This is a content-quality and navigation issue. It weakens the proposed chapter-page growth strategy and could cause readers to mistake figure/activity text for chapter names. The existing disclosure that the catalogue is not an official current-year CBSE syllabus is appropriate, but does not repair the labels.

**Action:** review extracted titles against the installed source, normalize chapter names and numeric ordering, and investigate the extraction pipeline rather than manually inventing titles. Build any future chapter pages around reviewed questions, explanations, provenance and useful practice actions. Do not publish hundreds of nearly identical title-only pages or claim official current-year alignment without verification.

**Acceptance:** a human-reviewed sample of each supported subject has recognizable complete chapter titles and correct numeric order; examples and unavailable curriculum remain clearly labelled.

### 4. P2 — Clarify umbrella search positioning without erasing Nearby

**Confirmed live:** root title is `Paper Shapers — A house of useful ideas`; H1 is `Two ideas. One useful internet.`; description is `Explore practical tools for learning and neighbourhood discovery — all under one independent umbrella.` These explain the brand but leave the actual product categories out of prominent metadata.

The Study landing page already has a descriptive title, `CBSE chapter practice papers and teacher Live Rooms · Paper Shapers`, and a relevant description. Nearby likewise has `Local events, offers and community notices · Paper Shapers`. The earlier report's homepage observation should not be generalized to these pages.

**Action:** give the root title/description a clear two-product explanation, and add a concise visible introduction naming CBSE chapter practice and local notices. Example direction, not an approved keyword target: `Paper Shapers | CBSE Practice Papers & Local Notices`. Keep Study-specific search intent primarily on Study pages. Refine the Study H1/supporting text naturally; avoid keyword repetition. Descriptive product-card and curriculum links matter more than rewriting every expressive anchor.

Keyword demand, competition and conversion intent have not been researched in this audit. Do that before finalizing keyword-to-page mapping.

### 5. P2 — Reconcile crawl blocking with public noindex pages

**Confirmed pass with caveat:** all three hosts serve `/auth` with `X-Robots-Tag: noindex, nofollow` and matching HTML robots metadata. Sampled dashboard responses also carry the noindex header. `next.config.ts` covers private workflows; layouts add metadata for papers, rooms and teacher rooms. The earlier claim that account exclusion was wholly unverified is resolved for the sampled routes.

Robots also disallows `/auth` and the dashboard/workflow paths. Google cannot read a page's noindex when robots blocks its crawl. Keep real account data protected by authentication regardless of robots. For publicly reachable sign-in and workflow entry pages whose goal is exclusion from search, review allowing crawling so their noindex can be observed. Retain deliberate crawl restrictions where appropriate, especially API endpoints; do not indiscriminately remove every disallow rule.

**Acceptance:** private data stays inaccessible without authentication; crawler-visible public account entry responses emit noindex; Search Console confirms intended exclusions. See [Google noindex requirements](https://developers.google.com/search/docs/crawling-indexing/block-indexing).

### 6. P3 — Complete brand/social metadata and structured identity

**Confirmed live:** root has no JSON-LD; Study already emits a `WebApplication` with `EducationalApplication` category. Root and portal samples lack `og:url`. The shared Apple web-app title is `Study`, and the shared manifest identifies the Study app even on the umbrella/Nearby host. Twitter metadata on portal pages inherits umbrella copy.

**Action:** add truthful Organization/WebSite identity with stable URLs and IDs; connect the existing Study application to that identity. Consider portal-specific social titles, descriptions, URLs and app metadata. Treat these as presentation/entity improvements, not guaranteed rankings or rich-result eligibility. Do not invent reviews, ratings, prices, endorsements or local business addresses.

Adding useful visible FAQs may help readers, but **do not prioritize FAQ markup as a Google rich-result opportunity**: Google's current changelog says FAQ rich results stopped appearing on May 7, 2026, and the documentation was removed in June. See [Google's documentation updates](https://developers.google.com/search/updates).

## Verified positives

- Root, Study and Nearby landing pages, robots files and sitemaps returned 200 via direct HTTP checks.
- HTTP root navigation ultimately resolves to HTTPS; root has a non-www canonical.
- Portal landing canonicals are already consistent with the documented subdomains.
- Titles/descriptions are present on sampled content pages; sampled content pages have one H1. This is not proof that every route has correct heading structure.
- Existing class and subject catalogue pages provide crawlable links and root-domain canonicals. New class/subject pages do not need to be invented from scratch.
- Sampled rendered image elements have alt attributes; this checks presence, not editorial quality or every image asset's availability/dimensions.
- The deliberately nonexistent route returns a real 404 and noindex on each host.
- One sampled fictional Nearby guide explicitly emits `noindex, follow`; dummy guides are excluded by sitemap source logic. Public content distinguishes examples from submitted notices.
- Privacy, terms, cookies, contact routes and educational disclaimers are present. These are useful trust elements, not ranking guarantees.
